# 会易达补充说明（README 与代码现状版）

本文档只基于以下两类信息整理：

- 根目录 README
- 当前仓库中的实际代码实现

不以历史讨论稿、旧需求文档、阶段性说明作为判断依据。

## 1. 当前项目定位

当前的 Meeting2Action 已经不是单纯的静态原型，而是一个可本地运行、可持久化保存、可演示核心业务闭环的 MVP。

它已经覆盖了一条完整主链路：

会议纪要输入 -> 解析为行动项 -> 导入任务 -> 落库 -> 看板查看与编辑 -> 会议与成员协同管理

从产品角度看，它已经具备“演示版”和“课程项目交付版”的核心形态，但还没有达到“最终产品版”或“可上线正式版”的标准。

## 2. 当前已具备的能力

### 2.1 本地可运行

- Web 前端可通过本地开发服务启动并在浏览器访问。
- API 后端可独立启动并提供 HTTP 接口。
- Windows 环境下可通过 `scripts/start-dev.cmd` 一键启动。

### 2.2 本地持久化

- 前端数据不是只存在页面内存中，而是统一通过后端接口写入本地 SQLite。
- 默认数据库文件为 `data/meeting2action.db`。
- 重新打开浏览器或重启前后端后，只要数据库文件仍在，数据可以再次读取出来。

### 2.3 会议纪要解析链路

- 支持粘贴文本和上传文本类文件。
- 支持 `auto`、`llm`、`heuristic` 三种解析模式。
- 当存在大模型配置时可走 Claude 或 OpenAI。
- 当没有可用 API Key 时，会自动回退到规则解析，不会阻塞系统整体运行。
- 解析记录支持保存、查询、删除，并可导入到看板。

### 2.4 任务与看板能力

- 已支持从行动项批量导入任务。
- 已支持手动创建任务。
- 已支持任务列表、任务详情、任务状态更新、负责人更新、截止日期更新。
- 已支持任务删除。
- 已支持任务关键词搜索与排序，后端已支持分页查询参数。
- 已支持任务活动记录查询。
- 已支持看板聚合数据与统计数据查询。
- 前端已具备三栏看板、任务详情抽屉、风险和负责人筛选等交互。

### 2.5 团队与会议管理

- 已支持成员的增删改查。
- 已支持会议的增删改查。
- 已支持参会人关系维护。
- 会议与成员、任务之间已经形成基本的数据联动。

### 2.6 用户与会话

- 已支持基于现有成员的本地登录会话。
- 前端刷新后可恢复当前登录成员。
- 后端已提供 `POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/users/me`。
- 任务、会议、纪要解析等写操作已接入登录校验。
- 成员创建支持“首个成员可匿名创建，后续创建需登录”的本地引导模式。

## 3. 当前版本的边界

以下内容不是“完全不可用”，而是说明该项目仍停留在 MVP 阶段，尚未补齐正式产品通常需要的能力。

### 3.1 用户体系仍是基础版

- 当前登录能力本质上是“成员即本地账号”的轻量会话模型。
- 已有登录、登出和当前用户接口，但还没有密码、角色、团队隔离、细粒度权限。
- 这意味着它已不是纯前端演示态，但仍不能等同于正式多租户产品。

### 3.2 检索与规模化使用能力仍不足

- 当前已支持关键词搜索、排序和后端分页参数。
- 但前端还没有完整分页界面、归档视图、批量操作等规模化管理能力。
- 当任务量继续增长时，现有工作台仍更适合中小规模团队使用。

### 3.3 数据约束仍可继续收紧

- 当前已经补上成员名称唯一约束和基础冲突错误。
- 但任务负责人仍保留 `ownerName` 文本回退逻辑，关系模型还没有完全收紧。
- 更完整的业务唯一性策略和更统一的错误码体系仍值得继续补强。

### 3.4 自动化能力尚未落地

- `apps/worker` 目录仍处于预留状态。
- 逾期扫描、消息提醒、周报生成等“系统主动工作”的能力还没有真正实现。
- 这部分恰恰是产品从“任务工具”走向“项目管理 OS”的关键差异点。

### 3.5 工程化与可靠性不足

- 当前缺少正式测试体系。
- 测试目录基本为空，脚本中也没有完整测试命令。
- 这意味着当前版本更适合开发调试和展示，不适合高频迭代后的稳定交付。

### 3.6 输入场景还不够完整

- 当前会议输入主要是文本和文本文件。
- 若产品目标是覆盖真实会议场景，后续通常还需要补录音、转写、更多导入源。

## 4. 是否可以视为“完整项目”

答案取决于评价标准。

### 如果标准是课程作业 / 演示项目

可以。

原因是它已经具备以下完整闭环：

- 前端界面可访问
- 后端服务可运行
- 数据可落库
- 核心业务链路可演示
- 任务、会议、成员三块主体能力均已存在

### 如果标准是最终产品版 / 可上线版

还不可以。

当前更准确的判断是：

这是一个已经成型的 MVP，而不是最终产品版。

## 5. 离最终版还差哪些关键能力

建议按优先级理解，不建议把所有事项看成同等重要。

### P0：必须补齐

#### 1. 权限模型升级

- 角色或权限控制
- 数据按用户或团队维度隔离
- 不同资源写操作的更清晰授权边界

#### 2. 任务管理规模化补齐

- 前端分页或加载更多
- 归档或历史视图
- 批量操作

#### 3. 最低限度自动化测试

- 核心 API 烟雾测试
- 任务服务核心逻辑测试
- 成员和会议关键路径测试

#### 4. 关系与错误处理继续收紧

- 更稳定的关系数据一致性
- 更统一的错误码和异常语义
- 逐步减少对 `ownerName` 文本回退的依赖

### P1：提升产品价值

#### 1. Worker 异步任务

- 逾期扫描
- 提醒生成
- 周报汇总

#### 2. 全局活动流

- 最近谁创建了任务
- 谁更新了会议
- 哪些任务发生了状态变化

#### 3. 更完整的统计与汇总视图

- 团队维度统计
- 周期性进展汇总
- 风险任务概览

### P2：增强真实场景适配能力

#### 1. 会议录音/转写接入

- 音视频导入
- 自动转写
- 转写后进入解析链路

#### 2. 导出与共享能力

- 周报导出
- 任务清单导出
- 会议信息导出

#### 3. 部署与运维补充

- 更明确的环境变量管理
- 生产启动方式
- 日志与错误监控

## 6. 建议的最终冲刺顺序

如果时间有限，建议按下面顺序补，而不是平均发力。

1. 角色与权限边界
2. 基础测试
3. 分页、归档与批量操作
4. Worker 提醒能力
5. 输入场景扩展

这条顺序的理由很直接：

- 前三项决定它能不能从“可演示 MVP”走向“更稳的产品版”。
- 后两项决定它能不能体现智能项目管理的差异化价值。

## 7. 一句话结论

当前的 Meeting2Action 已经是“可运行、可落库、具备基础登录会话、可演示主业务闭环的 MVP”，但距离“最终产品版”仍然至少差一层权限模型、一层自动化能力和一层工程可靠性。

如果只以答辩和演示为目标，它已经接近完整。
如果以正式产品为目标，它还处在从 MVP 走向产品化的中段。
